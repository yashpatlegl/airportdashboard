Versioned migrations — one concern per version
V1
Create Airport Dashboard — structure
Table airport_dashboard: BIGSERIAL key, entity identifier and type, ICAO / IATA, airport name, location, procedure, MITS, effective date, status, remarks, full audit columns, soft-delete columns and an optimistic-locking version.
V2
Constraints — integrity
UNIQUE(entity_identifier) · regex CHECKs for ICAO ^[A-Z]{4}$ and IATA ^[A-Z]{3}$ · allowed entity_type and the ten workflow status values · version >= 1 · a deleted row must carry deleted_at.
V3
Indexes — performance
Partial indexes on every filter and sort column (status, entity type, ICAO, IATA, location, effective date, updated at) plus the composite (status, updated_at DESC). All are declared WHERE is_deleted = FALSE, so they stay small and match the queries the dashboard actually runs.
V4
Data migration — normalisation
UPPER / TRIM of codes and identifiers, audit backfill for legacy rows, empty strings converted to NULL. Runs before the data has to satisfy the constraints added in V2.
V5
Seed data — reference set
Twenty AOM records covering all ten workflow statuses, so a fresh environment renders a meaningful dashboard immediately.

On every startup Flyway compares this ledger with the files on the classpath: already-applied versions are skipped, new versions are applied in order, and a changed checksum on an applied version fails the migration instead of silently diverging.

Configuration in useapplication.yaml

spring.flyway.enabled: true locations: classpath:db/migration baseline-on-migrate: true spring.jpa.hibernate.ddl-auto: validate
baseline-on-migrate lets Flyway adopt a database that already contains tables: the existing state becomes the baseline and only later versions are applied.
Who is allowed to change the schema

Flyway — creates and modifiesthe single writer of DDL

  • Owns CREATE, ALTER, index and constraint changes
  • Same ordered scripts run on local, test and production
  • Every change is reviewable, repeatable and attributable

Hibernate — validates onlyddl-auto: validate

  • Compares entity mappings against the live schema at startup
  • Fails fast on a mismatch instead of guessing or patching
  • Never issues DDL — no update, no create-drop, in any environment

Why not ddl-auto: update?the failure mode being avoided

  • Silently mutates production schemas with no history
  • Cannot express data migration, renames or backfills
  • Drifts between environments and can never be replayed
Applied migrations are immutable. A script that has already run is never edited — the checksum in the ledger would no longer match. A correction ships as a new version.
Sequential and ordered. Versions are applied lowest to highest, so structure precedes constraints, constraints precede data normalisation, and seed data comes last.
Adopting an existing database. When the target schema is not empty, baseline first and validate the current structure before applying constraint or data migrations.
